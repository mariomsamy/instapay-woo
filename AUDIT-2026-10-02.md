# Instapay Gateway for Egypt 1.2.0: logic and security audit

Date: 2026-10-02. Scope: `instapay-woo.php`, `includes/class-wc-gateway-instapay.php`, `assets/js/gateway.js`, `assets/css/gateway.css`, `readme.txt`.
Method: static review of every function and hook, plus `php -l` (passes). No running WordPress was available, so items marked **(verify)** depend on WooCommerce or browser behavior that should be confirmed on a staging site.

## Status after 1.3.0 (same day)

Every finding below was fixed in 1.3.0 and tested on a disposable WordPress 7.1.2 + WooCommerce 11.1.2 site (HPOS and posts storage). Testing also uncovered issues the static review missed:

| New finding | Severity | Result |
| --- | --- | --- |
| **N1.** `instapay_woo_use_receipts_upload_dir` called `wp_upload_dir()`, which re-applies the same `upload_dir` filter: infinite recursion, so **every receipt upload in 1.2.0 ended in "There has been a critical error"** (reproduced on the 1.2.0 code). | Critical | Fixed: the path is built from the filter's own `basedir`. |
| **N2.** Accepting moved the order `payment-review → processing`, a transition WooCommerce sends no customer email for. | Medium | Fixed: the transition is registered for the processing email. |
| **N3.** `wc_get_orders()` silently ignores `meta_query` on posts storage, so lookups by receipt hash returned unrelated orders. Found in the first 1.3.0 draft, never released. | High (draft only) | Fixed: `meta_key`/`meta_value`, which both stores support. |

Items marked (verify) were confirmed: B2 (drag and drop) was broken and is fixed; L10 is resolved by registering display hooks once in the main file. S2 (Imagick metadata) is resolved by re-encoding through GD; Imagick-only hosts remain untested.

Release notes: [RELEASE-NOTES.md](RELEASE-NOTES.md).

## 1. Architecture summary

A single WordPress plugin with no Composer or npm dependencies.

| Part | Where | Role |
| --- | --- | --- |
| Gateway class | `class-wc-gateway-instapay.php` | Settings, `process_payment`, thank-you/view-order upload form, admin meta box |
| Upload endpoint | `wp_ajax(_nopriv)_instapay_upload_receipt` | Customer uploads receipt (order key + nonce) |
| Optional REST | `POST /wp-json/instapay-gateway-for-egypt/v1/receipt` | Same upload, order key only, off by default |
| Manager action | `wp_ajax_instapay_quick_action` | Accept / reject / cancel (`edit_shop_orders` + nonce) |
| Receipt viewer | `init` hook on `?instapay_view_receipt=1` | Streams the image after nonce + ownership checks |
| Cron | `instapay_woo_cleanup_cron` (daily) | Deletes receipts on old failed/cancelled/refunded orders |
| Admin UI | dashboard widget, order-list column | Review queue |
| Storage | `uploads/instapay_receipts/`, order meta `_instapay_receipt_path`, `_instapay_receipt_filename` | |

Order lifecycle today: checkout → `pending` (stock reduced) → customer uploads → `payment-review` → manager accepts (`processing`), rejects (`pending`) or cancels (`cancelled`).

## 3. Findings

Severity: Critical / High / Medium / Low. Numbers are referenced from the call map.

### Business logic

**L1. High: the gateway does not appear in the block checkout.**
- Where: whole plugin. No `woocommerce_blocks_payment_method_type_registration` integration and no `cart_checkout_blocks` compatibility declaration.
- Impact: WooCommerce has used the block checkout by default since 8.3, and the plugin requires 8.5+. On a fresh store Instapay is not offered at all. It only works on stores that still use the `[woocommerce_checkout]` shortcode.
- Fix: add a small `AbstractPaymentMethodType` class and a JS registration script (no React build needed; `registerPaymentMethod` with a plain element works), then declare `cart_checkout_blocks` compatibility.

**L2. High: orders wait in `pending`, which WooCommerce auto-cancels and never emails about.**
- Where: `class-wc-gateway-instapay.php` `process_payment` (`update_status( 'pending' )`), and reject → `pending` in `instapay_woo_quick_action`.
- Root cause: `pending` means "payment not started" to WooCommerce. With stock management on, `wc_cancel_unpaid_orders` cancels `pending` checkout orders once the "Hold stock" time passes (60 minutes by default).
- Impact:
  - A customer who takes longer than the hold time to transfer and upload loses the order.
  - A rejected order goes back to `pending` and is cancelled 60 minutes after the rejection.
  - WooCommerce sends no customer email for `pending` orders and no "New order" email to the store. A customer who closes the tab gets no payment instructions, and a guest has no link back to the upload form. The store is not told about the order until a receipt arrives.
- Fix: use `on-hold` like the built-in bank transfer (BACS) gateway, keep accepting uploads in `pending` for existing orders, and add the instructions and an upload link to the on-hold email (`woocommerce_email_before_order_table`). If unpaid orders should still expire, add an explicit setting and expire them in the plugin's own cron.

**L3. High: the same receipt can be used to pay for several orders.**
- Where: `instapay_woo_process_upload_file`. Nothing identifies a transfer.
- Impact: a customer pays once and uploads the same screenshot to two orders. Different managers, or the same manager on different days, approve both. This is the main fraud path for manual-proof gateways.
- Fix: store a SHA-256 hash of the uploaded file (before re-encoding) in order meta and warn the manager in the meta box when another order has the same hash. Optionally ask the customer for the Instapay transaction reference and enforce uniqueness the same way.

**L4. Medium: the manager can approve a receipt they never saw.**
- Where: `instapay_woo_order_accepts_receipt` allows uploads in `payment-review`; `instapay_woo_quick_action` checks only that some receipt exists.
- Impact: the manager opens receipt A, the customer uploads receipt B, the manager clicks Accept, and B is approved without review.
- Fix: send the displayed `_instapay_receipt_filename` with the action and reject the action if it no longer matches. Optionally also block uploads while in review.

**L5. Medium: accept, reject and cancel are not safe when they arrive twice.**
- Where: `instapay_woo_quick_action`. It reads the status, checks the allowlist, then calls `update_status`. There is no atomic compare-and-set.
- Impact: two managers, or two open tabs, both pass the `payment-review` check. Each `update_status` runs the `payment-review → processing` transition, so the customer gets two "processing" emails and integrations (ERP, shipping, accounting) hooked to `woocommerce_order_status_processing` run twice. A double reject sends two rejection emails.
- Fix: take an atomic per-order lock (an `INSERT … ` that fails on the unique key; see L7), re-read the order inside the lock, re-check the transition, then update.

**L6. Medium: an upload can bring a cancelled order back to life.**
- Where: `instapay_woo_handle_receipt_upload` and `instapay_woo_rest_upload_receipt`. The status is checked before the file is processed (image re-encoding can take seconds), and `update_status( 'payment-review' )` is then called on an order object loaded before processing.
- Impact: if the manager or the hold-stock cron cancels the order during the upload, the stale object sets it to `payment-review` anyway. The cancellation is silently reversed, and its stock was already restored.
- Fix: after processing, reload the order and re-check `instapay_woo_order_accepts_receipt` inside the lock before changing status. Delete the new file if the check fails.

**L7. Low: the upload lock is not atomic.**
- Where: `instapay_woo_acquire_upload_lock`. It reads the option, deletes a stale one, then calls `add_option`. `add_option` uses `INSERT … ON DUPLICATE KEY UPDATE`, so a second request that reaches it in a different second gets a truthy result and also "acquires" the lock.
- Impact: the window is small, but two uploads can run together. Each deletes the previous receipt and only one file ends up in meta. The other becomes an orphan on disk (see Q3).
- Fix: `$wpdb->query( $wpdb->prepare( "INSERT IGNORE INTO {$wpdb->options} (option_name, option_value, autoload) VALUES (%s, %s, 'no')", … ) )` and treat 1 affected row as acquired. Expire stale locks with a single conditional `DELETE … WHERE option_value < %d`.

**L8. Low: the customer sees wrong messages after the review ends.**
- Where: `thankyou_page`.
- Impact:
  - A `processing` or `completed` order still says "Your payment is under review."
  - A cancelled or refunded order with a receipt says "Your previous receipt was rejected. Please upload a new valid screenshot," but no upload form is shown.
- Fix: choose the message by status: review, accepted, rejected (`pending`/`failed` with a receipt), or closed.

**L9. Low: the rejection email link sends the customer to the wrong page.**
- Where: `instapay_woo_quick_action` uses `get_checkout_payment_url()`. That is the order-pay page, where the customer has to pick a method and press Pay again before the upload form appears. Guests may also be asked to verify their email first.
- Fix: link to `$order->get_checkout_order_received_url()`, which shows the upload form straight away.

**L10. Low: some hooks only exist if WooCommerce has already created the gateway object (verify).**
- Where: the gateway constructor registers `woocommerce_view_order`, `woocommerce_receipt_instapay` and `add_meta_boxes`. These only exist after WooCommerce instantiates gateways, which happens lazily.
- Impact: if a page loads without instantiating gateways, the upload form on My Account or the admin meta box can be missing. If anything instantiates the class twice, the form renders twice and `#instapay_rejection_reason` is duplicated.
- Fix: register these display hooks once from the main plugin file, calling a static renderer.

### Security and privacy

**S1. Medium: uploads have no rate limit or count limit.**
- Where: both upload endpoints.
- Impact: anyone with an order key (any customer, for their own order) can upload repeatedly. Each upload costs CPU for re-encoding and sends the store an email with up to a 5 MB attachment. That allows mail flooding and resource exhaustion.
- Fix: cap uploads per order (for example 5 per hour, counted atomically in order meta or the options table), and send the admin email only on the first upload per review cycle.

**S2. Medium: image metadata is not always removed (verify).**
- Where: `instapay_woo_process_upload_file`. It relies on `$editor->save()` to drop metadata.
- Impact: GD re-encodes and drops EXIF. With Imagick (the default on most hosts) metadata is stripped only inside `resize()`, and `resize()` returns early when the image is already smaller than 1200 px or compression is off. Phone photos of a screen can keep GPS and device data.
- Fix: for Imagick editors call `strip_meta`, or re-encode through GD; alternatively always call `resize()` with the original dimensions.

**S3. Medium: very large images can crash the upload.**
- Where: `instapay_woo_process_upload_file`. Only the byte size is limited to 5 MB. A highly compressible PNG or WebP can decode to tens of thousands of pixels.
- Impact: PHP memory exhaustion is a fatal error, so the lock stays for 120 s and an orphan file is left in the receipts folder.
- Fix: read the dimensions with `wp_getimagesize()` first and reject anything over about 6000 × 6000 or 30 MP.

**S4. Low: on Nginx, and on hosts where `WP_Filesystem()` isn't direct, receipts are protected only by random names.**
- Where: `instapay_woo_ensure_receipts_dir`. If `WP_Filesystem()` fails (FTP-credential hosts), the `.htaccess`, `web.config` and `index.php` files are silently not written. Nginx ignores them anyway.
- Impact: receipts are reachable by direct URL. The names include the order ID plus 12 random characters, so they are not guessable, but they are still public if a URL leaks. The deny files are also rewritten on every upload.
- Fix: write the deny files with plain `file_put_contents` once (on activation or upgrade), and check for and warn in admin when they are missing. Longer term, move storage outside the web root (filterable path).

**S5. Low: the order key appears in the receipt image URL.** This matches what WooCommerce already does on the thank-you page, so it adds little risk. Noted because of the "no secrets in URLs" rule. Keep it unless the viewer moves to session-only access.

What checked OK:
- Receipt viewer authorization: nonce, then manager capability, owner, or `hash_equals` on the order key.
- Path canonicalization and confinement to the receipts folder.
- Upload type checks: extension plus real MIME plus `wp_get_image_mime`.
- Random filenames; `is_uploaded_file` is enforced by `wp_handle_upload`.
- Capability and nonce on the manager action, with a transition allowlist.
- Output escaping everywhere reviewed.
- No raw SQL, no mass assignment, no SSRF (the QR URL is only rendered client-side), no secrets in the repository.

### Platform bugs

**B1. Medium: uploads always fail on Windows servers.**
- Where: `instapay_woo_get_uploaded_file` calls `wp_unslash( $_FILES['instapay_receipt'] )`. WordPress does not add slashes to `$_FILES`, so this strips the backslashes from the temp path: `C:\Windows\Temp\php1A2B.tmp` becomes `C:WindowsTempphp1A2B.tmp` (checked with `php -r`).
- Impact: every upload fails the `is_uploaded_file` test on Windows/IIS, even though the plugin ships `web.config` rules for IIS.
- Fix: don't unslash `$_FILES`; read `tmp_name` as given.

**B2. Medium: drag and drop likely doesn't work (verify in browser).**
- Where: `gateway.js`. The file input is laid over the whole drop zone (`gateway.css`, `inset: 0`), and the drop zone's `drop` handler calls `preventDefault()`. The drop event bubbles from the input to the drop zone, and cancelling it stops the browser from putting the file into the input. Dropping just outside the zone opens the image in the tab and leaves the page.
- Fix: in the `drop` handler, copy `event.originalEvent.dataTransfer.files` into the input and trigger `change`, or stop calling `preventDefault` on `drop`.

### Data and performance

**Q1. Medium: the daily cleanup loads and saves every old closed order in the store.**
- Where: `instapay_woo_cleanup_receipts`. It uses `limit => -1` with no payment-method or meta filter, and `instapay_woo_delete_receipt` calls `$order->save()` even when there is nothing to delete.
- Impact: on a large store this loads thousands of orders of every gateway every day, fires order-save hooks for each one, and can exceed cron time and memory limits.
- Fix: filter on `payment_method => 'instapay'` and on the meta key existing, process in batches of about 100, and save only when meta was actually removed.

**Q2. Low: the order list does file work for every row.** `instapay_woo_render_order_column` calls `instapay_woo_get_valid_receipt_path` (a new order load, `realpath` and an image header read) for each Instapay order. Checking that the meta exists is enough for an icon.

**Q3. Low: crashed or concurrent uploads leave orphan files** (see L7 and S3). Nothing ever removes files that aren't referenced by an order. Add an orphan sweep for files older than a day to the cron.

**Q4. Low: the old receipt is deleted before the new one is saved.** If saving the order then fails, the order has no receipt. Save the new meta first, then delete the old file.

### Compliance (Egypt Law 151/2020 and the CLAUDE.md MENA checklist)

| Item | Status | Evidence |
| --- | --- | --- |
| Retention and purge of financial data | GAP | Receipts for `processing`/`completed` orders are kept forever. Cleanup is optional and covers closed orders only. There is no `uninstall.php`, so receipts, settings and lock rows remain after uninstall. |
| Notice and consent at collection | GAP | The upload form doesn't say what is stored, why, or for how long. Add one bilingual sentence with a link to the privacy policy, and use `wp_add_privacy_policy_content`. |
| Data-subject export and erase | GAP | Not registered with `wp_privacy_personal_data_exporters` or `wp_privacy_personal_data_erasers`, so WordPress's privacy tools ignore receipts. |
| Personal data in email | GAP | The admin email attaches the receipt image. Prefer a link to the protected viewer. |
| Personal data in logs or URLs | OK | No logging. The order key in URLs follows WooCommerce's own behavior (S5). |
| Third-party assets | C3 Low | The QR image is loaded from a URL the merchant enters, which may be an external host that logs customer IPs. Suggest uploading it to the Media Library. |
| Tracking, minors, marketing, subscriptions, UGC | N/A | None present. |
| VAT and invoice display | N/A | Handled by WooCommerce, not this plugin. |

### Code quality and documentation

- `in_array( $new_status, array( 'processing', 'completed' ) )` in the quick action: `completed` can never reach this line.
- The `woocommerce_receipt_instapay` hook never fires in the current flow, because `process_payment` redirects to the thank-you page.
- The meta box is added to every order and says "not paid via Instapay" on others. It should only be added for Instapay orders.
- The audit note shows the raw status slug (`processing`) inside translated text. `sprintf` calls with placeholders have no `translators:` comments.
- `readme.txt` claims things the code doesn't do:
  - "converted to modern formats": no format conversion happens.
  - "deletes rejected… receipts": rejected orders are `pending` and are never cleaned.
  - ".htaccess rules prevent direct access": not true on Nginx.
  - "enterprise-grade" marketing text.
- The upload and email paths have no failure logging. `wc_get_logger()` with order ID and error code, and no personal data, would make support possible.
- No automated tests.
- `.DS_Store` and the built zip sat in the source folder.

## 4. Proposed fixes, in order

1. B1: remove `wp_unslash` on `$_FILES`. One line.
2. L6, L7, L5: an atomic per-order lock helper; re-read and re-check the order inside the lock for both uploads and manager actions.
3. L4: bind Accept to the displayed receipt filename.
4. L3: receipt hash plus a duplicate warning in the meta box.
5. S1, S3, S2: an upload count limit, a dimension check before decoding, and explicit metadata stripping.
6. Q1, Q2, Q4: scoped and batched cleanup; a lighter list column; save before delete.
7. L2: move to `on-hold` with instructions in the email. **This changes store behavior and needs your decision.**
8. L1: block checkout support. New files; the largest change.
9. B2, L8, L9: drag-and-drop, status messages, rejection link.
10. Compliance: `uninstall.php`, privacy exporter and eraser, a retention setting, an upload notice, and a link instead of an attachment.

Each fix keeps the existing option keys, meta keys, hooks and the REST route unchanged.
